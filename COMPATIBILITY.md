# Backward-compatible RSA migration

## Existing applications and data

The module remains `github.com/Laisky/go-yubikey/v2`. All pre-existing exported signatures keep `github.com/go-piv/piv-go/piv` concrete types. Listing cards, attestation, signing, ECDH and management-key operations retain their implementations and v1 array-based management APIs/3DES behavior. No key reset, new key generation, PIN change or ciphertext rewrite is required to upgrade the library.

`Decrypt` keeps its old RSA PKCS #1 v1.5 selection; `DecryptLegacy` is the explicit equivalent. Valid canonical ciphertext previously generated by `go-utils/v6 v6.2.1 RSAEncrypt` remains decryptable. Retained synthetic fixtures cover RSA-1024/2048, one-byte and binary plaintext, `k-11` maximum capacity and full-width leading-zero ciphertext. Empty encryptor output and concatenated/chunked output are unsupported single-device-wrapper framing controls, not newly removed supported formats. No real user ciphertext or keys were read.

The actual historical encryptor returns raw RSA bytes with no version or algorithm tag. Ciphertext length alone cannot identify PKCS #1 v1.5 versus OAEP. Existing datasets must be treated according to their known provenance; the library does not guess. The separate consumer ECIES/ECDH format is a different protocol and is not changed by these APIs.

## Explicit new-data operation

`EncryptOAEP` and `DecryptOAEP` select SHA-256, MGF1 SHA-256, an empty label and exactly one modulus-sized RSA block. They support the same RSA-1024/2048 PIV algorithms as the v1 backend. Capacity is `k-66`, and oversized plaintext is rejected. All decryption errors return nil plaintext. There is no OAEP-error-to-legacy fallback.

The application's root `go.mod` must explicitly select the compatibility fork:

    replace github.com/go-piv/piv-go => github.com/Laisky/piv-go <pinned-version>

Use the exact reviewed version from this repository's `go.mod`. The fork declares the original module namespace and keeps original internal imports, preserving public type identity and selecting a single PIV implementation. A dependency's replacement does not propagate to an application. Without the replacement, old APIs build and behave as before; `DecryptOAEP` fails closed with `ErrOAEPUnsupported` before private decryption, rather than trusting ignored options. Its capability check is structural and depends on the concrete reviewed RSA implementation, not a guessed version or trial decryption.

For an application-created versioned record, select the operation from a trusted algorithm/version field: historical PKCS #1 v1.5 records use `DecryptLegacy`; new OAEP-SHA256 records use `DecryptOAEP`. Never change an existing unversioned record's meaning, and never choose a second algorithm after a decoding failure. This patch does not invent a new on-disk envelope or alter the user's unseen dataset.

## Retained legacy risk and testing limits

Preserving arbitrary-message PKCS #1 v1.5 means its padding-oracle risk remains. The reviewed decoder validates framing/padding and honors explicit options, but these improvements do not make the legacy protocol safe against an observer who can submit chosen ciphertext and distinguish outcomes or timing. Error wrapping, PIN and touch do not establish removal of this risk. Keep legacy use restricted to trusted historical data and controlled migration; new untrusted decrypt endpoints should accept only the explicit OAEP contract.

The fork's stricter malformed-padding/framing checks and honored options change invalid-input edge behavior. Valid historical encryptor fixtures are the compatibility gate; undocumented serialization variants and a physical card still require acceptance evidence.

Tests distinguish: exported-wrapper behavior with only device/key acquisition mocked and real software RSA; concrete fork RSA/APDU decoder with only the card's raw private operation mocked; and a real public fork key handle whose test PIN callback deliberately stops before any transaction. None establishes physical firmware/transport/PIN/touch behavior or a timing-oracle result. Default tests skip all physical access. Destructive reset tests are separately disabled.
